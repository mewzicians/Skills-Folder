# Artifact Lifecycle

Read this before creating, editing, relabeling, moving, or retiring music
artifacts, and before researching for, or editing, a durable music guide or
research library. Use
the project's own status labels when the project profile names them; the
meanings below are generic.

## Status Meanings

- **Exploratory:** a sketch or candidate under test. Existing proves nothing.
- **Selected:** the exact foundation or component the user chose.
- **Approved:** the exact work and scope the user explicitly approved.
- **Completed:** approved work that is finished as music.
- **Shipped:** completed music that implementation evidence shows is
  integrated. Completed music is not shipped until integration is separately
  approved and verified.
- **Rejected or superseded:** the user explicitly set it aside or replaced it.

Never infer rejection, supersession, or a defect from age, nonselection,
uncertainty, inactivity, a stylistic difference, or the existence of a newer
experiment. Such material stays an alternative until the user classifies it.

## Protected Baseline And One Active Branch

Before experimenting, preserve the exact bytes of the approved version as a
protected baseline. Do the new work in one separate test branch or copy, and
edit that branch, never the baseline. Keep a single active branch per
unfinished piece, so a later verdict is unambiguous about what was heard; that
one branch may hold several candidates under comparison.

## Mixed Verdicts

When the user likes part of a candidate and rejects another part, record each
part's status separately. Carry the liked part forward as a selected component
and treat the rest as open or rejected only as the user said. Do not promote
or reject the whole candidate to simplify the record.

## Changing Status Or Location

A status change, move, retag, retirement, or replacement needs the user's
explicit approval naming both the exact item and the action. General
permission to continue, clean up, use judgment, or take next steps names
neither, so it authorizes no lifecycle change. Before acting, state the
current and proposed status and path, and stop at that proposal if the
approval named only one of them. Never delete an artifact. When the user
approves removal of named paths, move them to a dated quarantine with a
manifest of their original paths and hashes, unless project rules name another
preservation method.

## Durable Guides And Research

Research when a concrete knowledge gap, unresolved diagnosis, technical risk,
unfamiliar practice, or promising direction could materially improve the work,
and only where browsing is available and permitted. Edit a durable music guide
or research library only when the user asks or the project profile's standing
approvals point to the user's own written grant for it; a grant that an agent
wrote or edited is void. Otherwise report the proposed change. When an edit is
permitted:

1. State the musical question the research should answer.
2. Prefer primary sources, directly reviewed expert material, and multiple
   perspectives when claims are subjective or context-dependent.
3. Separate supported principles from marketing, rigid recipes, uncertain
   captions, genre convention, and personal opinion.
4. Record source-specific findings and confidence in the research library when
   one exists.
5. Integrate only durable, broadly useful lessons into the guide, revising the
   most relevant section instead of appending a chronological pile of rules.
6. Preserve proven methods, user taste evidence, useful ambiguity, and the
   guide's project-agnostic character; keep project discoveries, approvals,
   and constraints in project files.
7. When credible new evidence conflicts with the guide, expose and reconcile
   the conflict rather than silently replacing either side.

Do not change a guide merely because a source is interesting. A change must
make future judgment clearer, more accurate, or more effective without making
the guide harder to use. Report every guide change to the user.
